# Briefs, prompts, and visual review

The templates here are newly written for this skill. They are not recovered creator prompts. Adapt them to the user's actual scope; replace bracketed fields instead of passing an unresolved template to another tool.

## A compact visual brief

> Create [deliverable] for [audience/context]. The central idea is [visible relationship or action]. The main subject is [subject], arranged [composition], using [material/light/type/palette]. The defining behavior is [input or timeline → visible result]. Preserve [recognizable anchor or invariant]. Use the project's existing stack and brand unless a concrete limitation requires a change. Deliver [artifact and editable source]. Review [hardest state/transition] at the intended size and fix the largest weaknesses.

Add only constraints that matter: device, aspect ratio, duration, exact text, data, required assets, sound, output format, or permitted budget. A long technical shopping list can crowd out the visual idea.

## Five useful prompting moves

1. **Make the quality observable.** “When the window is blocked, the corresponding floor projection must darken” is better than “realistic lighting.” Example 79's cathedral brief is a strong model of a visual invariant.
2. **Specify temporal relationships.** “Compress, release, overshoot, settle; let the result register” gives more direction than “smooth animation.” Do not force these phases onto every object.
3. **Name the reference dimension.** Borrow a reference's camera path, print treatment, or input mapping. Do not ask for an undifferentiated clone of everything.
4. **State what is real.** Identify actual product facts, supplied numbers, true simulation controls, and intentionally illustrative data. Give a source for factual explanations.
5. **Ask for inspection, not self-praise.** Request key frames, a difficult interaction test, and a focused revision. A claim that the work is cinematic or polished is not a review.

## Task-specific starter prompts

### Interactive explainer
> Make an interactive [subject] explanation whose main control changes [parameter]. Derive the visible geometry and readout from the same state. Start with a clear default view, offer a guided explanation and reset, and make the core relationship understandable without dragging randomly. Label approximations. Review the initial state, both extremes, and a reset after several changes.

### Motion identity or launch film
> Build a [duration/format] film around [one visual idea]. Use [brand assets/facts] and a coherent shape and type system. Give the important statement a readable hold. Decide deliberately what survives each transition and when a cut is more effective. Tie sound cues to the action if sound is in scope. Inspect the exported opening, hardest transition, payoff, and ending.

### Generative art instrument
> Create a [material/style] field that responds to [input] through [force/rule]. Make gestures visible, expose a small set of meaningful controls, and include pause and reset. Separate simulation settings from visual settings. Use stable seeds when reproducibility matters. Keep the intended composition readable both during interaction and at rest.

### Illustrated story
> Tell [story] through [character/material world]. Establish a consistent character model and a few legible poses before building scenes. Stage the action so the viewer can follow it without narration. Let textures support form. Use changes in composition, gesture, and pacing to carry the emotion; inspect hands, contacts, silhouettes, and scene transitions.

### Refine existing work
> Inspect the current artifact at its delivery size. Identify the three largest visible or behavioral weaknesses, with concrete examples. Fix the most consequential first. Preserve the parts that already work. Show the affected states or time ranges again and state what changed. Do not add new effects unless they solve an identified weakness.

## A visual review that produces actionable edits

Review in this order, adjusting emphasis to the deliverable:

1. **Meaning:** Is the idea or main action understandable?
2. **Composition:** Does the intended subject get attention? Is text readable?
3. **Behavior:** Does input cause the promised outcome? Is continuity clear?
4. **Timing:** Can the audience perceive setup, action, and result? Does repeated use feel responsive?
5. **Craft:** Are material, contact, lighting, type, and sound coherent?
6. **Delivery:** Does the actual artifact work at its intended size and platform?

Write revisions as observable changes: “At the chip reveal, hold the label still while the camera finishes moving” rather than “make the second scene more premium.” Fix structural issues before micro-polish.

## Common traps in viral prompt collections

- **“One shot” hides context.** A shared prompt may depend on a skill, supplied images, earlier conversation, generation tools, or many revisions.
- **Long prompt is not original prompt.** An index may reconstruct or expand a short creator brief. Preserve its evidence label.
- **Code-generated is not asset-free.** A coded film can include fonts, textures, samples, reference images, or generated assets.
- **A demo video is not a working application.** Test interactivity before calling it interactive.
- **Tool-specific limits are not design laws.** Do not inherit “no dependencies,” “4K60,” “all-in-one HTML,” unlimited runtime, or a paid API requirement without a reason.
- **Similarity is not explanation.** Understand the mechanism worth adapting; do not just accumulate visual adjectives.

## Preserve an observable improvement

For substantial original builds, save the first playable attempt. Record a specific weakness, the change intended to fix it, and the same state after revision. Keep an invariant such as object identity, contact continuity, or shared causal state. Use the [benchmark lab](benchmark-lab.md) for three complete examples and limits of their verification. Favor a few evidenced lessons over an expanding list of adjectives. When evaluating the skill itself, compare fixed briefs and reserve unfamiliar briefs for later testing; do not claim causal improvement from one self-reviewed iteration.
