# Hand and depth input for responsive visual matter

## Evidence and its limits

The [September 29 Opus 5.5 water-orb post](https://x.com/nao_1000ri/status/2104845704997019793) shows a browser effect with luminous hands and a deforming orb. In the [creator follow-up](https://x.com/nao_1000ri/status/2104875907861377495), Nao names MediaPipe for joints and Depth Anything V2 through Transformers.js/WebGPU for depth, both in workers. The original recording was played and sampled near 12 seconds: hand meshes, webcam landmark overlay and a deformed orb were visible. No live camera session, creator source, solver, depth calibration, latency or sound was tested. “Real fluid” remains a creator claim.

The [official MediaPipe worker sample](https://github.com/google-ai-edge/mediapipe-samples-web/blob/fa5a2eec5a6a3bed339d872dfd8d7895e1db13f7/src/workers/hand-landmarker.worker.ts) was read at revision `fa5a2eec5a6a3bed339d872dfd8d7895e1db13f7`. It passes a timestamp into video detection, closes input bitmaps and posts detection results with inference duration. Its result message does not carry a frame ID or the capture timestamp; add these when pairing independently computed streams. Apache-2.0 header inspected; source is linked, not bundled or executed.

[Hugging Face's depth guide](https://github.com/huggingface/transformers/blob/main/docs/source/en/tasks/monocular_depth_estimation.md) distinguishes relative depth from metric distance and names Depth Anything V2 as a relative-depth example. The creator did not identify the exact checkpoint. Verify the selected model's semantics before choosing units; a depth visualization is not automatically meters. One generic pipeline sentence in that guide calls values meters despite its relative-depth example, so do not infer units from that sentence alone.

## Original implementation recipe

1. **Prove alignment before the effect.** Show the captured frame, detected fingertip and sampled depth location together. Establish one unmirrored source-image coordinate system. Record each model's resize, crop and padding transform; map outputs back there before sampling. Apply display mirroring only once. Check left/right edges, portrait crops and camera changes. Keep a pointer fallback for developing the effect without camera access.
2. **Join by capture, not completion time.** Assign each captured image a monotonically increasing `frameId`, capture timestamp and session generation. Feed a copy of that same image to each worker. A transferable bitmap cannot be transferred to two workers: create independently owned inputs or coordinate their ownership. Return the identifiers with both outputs. For the baseline implementation, combine only matching-frame results; discard incomplete pairs after a measured timeout and bound the pending map. A newer hand result paired with older depth can move the sampled surface to the wrong object.
3. **Bound work and reject stale results.** Keep at most one active request and one replaceable pending capture per branch. On completion, publish only a complete pair newer than the current pair and younger than the permitted input age. Increment the session generation on camera switch, reset or restart; discard late results from older sessions. If exact pairing is too slow, explicitly choose a bounded-skew scheme and test it; do not quietly substitute whichever depth map is latest. Reuse the [stale-frame presentation principles](timing-and-presentation.md).
4. **Map perception into an authored control space.** Begin with a fingertip or palm marker driving a simple probe sphere. For relative depth, use a documented near/far interaction range with stable calibration; do not relabel it as physical distance. Avoid independent per-frame min/max scaling, which can make a stationary hand pump the object when the background changes. Reject out-of-image samples. Use robust local samples only within a plausible hand region; sampling across a silhouette can pull in background depth. Filter with elapsed time and clamp input speed before enabling strong impulses.
5. **Make loss of tracking safe for the scene.** Use fresh valid detections to enable contact; fade influence to zero when hands disappear or data ages out. Retain stable hand identity through crossings instead of relying on array order. After reacquisition, reset velocity history so the first jump cannot kick the object. Measure palm-relative gesture distances if apparent hand scale changes; tune thresholds with hysteresis to avoid flickering between states.
6. **Connect input to visible consequences.** Drive a bounded contact proxy from the accepted pair. Show its position while tuning forces or deformation, then reveal the finished material. Separate input smoothing from the simulation's integration step; a slower detector must not change solver time. Use modest interaction strength until the proxy visibly aligns with the hand, then tune radius, gain, damping and recovery. None of this specifies or validates the creator's fluid solver.

## Failure checks and tuning

Inject mismatched IDs, out-of-order completions, a stalled depth branch and results from a previous camera session. Only a valid current pair may affect the object. Test one hand leaving frame, two hands crossing, a mirrored preview, a resized input and a cluttered background. Review both the proxy overlay and the polished effect; bloom can hide misalignment. Profile capture-to-visible-response age separately from inference duration and display FPS. Verify camera-off cleanup and fallback behavior in the actual target browser.

Expose input-age limit, pair timeout, interaction depth range, filter response time, contact radius and maximum impulse. Treat values as measured design choices, not universal defaults. For a gallery installation, prioritize predictable recovery and a clearly discoverable gesture over adding more gesture classes.

**Adapted prompt:** Build a hand-driven [material sculpture] whose input alignment is inspectable. Pair hand and depth results by capture identity, preserve coordinate transforms, and fade contact when tracking becomes stale. Map relative depth into an explicit artistic range. First prove a simple contact proxy, then add the material. Provide a pointer fallback and report measured latency separately from visual quality.
