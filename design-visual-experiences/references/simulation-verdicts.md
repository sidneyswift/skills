# Make a simulation explain its outcome

Use this when the experience asks a viewer to discover why a system succeeds or fails: a balancing sculpture, sorting machine, material experiment or interactive science exhibit. Extend [contact-driven physics](patterns/physics.md#rigid-body-chain) and the [causal benchmark](benchmark-lab.md); do not add a dashboard to every artwork.

## Original build recipe

The following interface and implementation choices are new synthesis, not claims about the source UI.

1. **Choose the visible question.** For a balancing sculpture: can the object stay inside its support region after a push? Name the event, the sustained conditions and the time window separately. Avoid treating proximity to a target as completion.
2. **Use one authoritative snapshot.** A fixed update produces `{runId, tick, simTime, poses, conditions, verdict}`. Geometry and its annotations consume that same snapshot. Reset changes `runId`; reject delayed messages from the previous run. If you interpolate poses for display, mark measurements as sampled rather than inventing interpolated contact results.
3. **Make the unresolved condition visible.** Use a small halo on the relevant contact, a velocity trail that shortens as motion settles, and a compact dwell ring. Keep labels local to the object. During failure, retain the specific cause briefly so the viewer can connect the event to its consequence. Color supports shape and text rather than carrying the explanation alone.
4. **Accumulate uninterrupted simulation time.** Reset the dwell duration whenever any required condition becomes false. Pausing adds no time; one step adds exactly one simulation interval. Declare completion only when every condition stays true for the required dwell before the deadline. Decide explicitly whether leaving the target after completion revokes success or starts a new attempt.
5. **Offer a meaningful counterfactual.** Save a failing preset and a passing preset that change one policy or parameter. Replay from the same initial state and seed. Align comparisons at the relevant event, such as first contact, while retaining their actual elapsed times. Let a viewer switch the cause without changing the scoring rule.
6. **Preserve scale and scene assumptions.** If the object cannot fit, show that constraint. A redesigned object is a labeled variant with its own results. Never quietly stretch the scene to make the demonstration pass.

**Tune:** target tolerance, velocity threshold, dwell time, deadline, input impulse and one control policy. Choose ranges that expose interesting near misses as well as success. Units and thresholds belong to the specific experience; the source's robot values are not universal presets.

**Failure checks:** briefly entering the target must not pass; leaving and re-entering restarts dwell; paused wall time earns no progress; reset during an in-flight update must not restore the old scene. Identical saved configurations should produce comparable outcomes within the chosen solver's tolerances. Compare single-step and continuous execution at matching ticks.

**Adapted prompt — original:** Create an interactive [subject] where the viewer can test [causal question]. Establish a clear silhouette and one primary manipulation. Show arrival, sustained stability and completion distinctly, with a local indicator for the remaining condition. Include a repeatable failing preset and a passing preset that changes one cause. Drive the scene and explanations from the same state; make reset and pause coherent. Preserve the project's visual language and provide an equivalent reduced-motion explanation.

## Keep the evidence of a failed attempt

[The Mistake Machine](https://claude.ai/artifact/UT65BgFXk5AgwDaLeGb6Cr), linked by its [September 29 creator post](https://x.com/CurieuxExplorer/status/2104787439541981676), credits Opus 5.5. Selected live interactions showed progressive path revelation and an unknown-area percentage. In its two-process comparison, the right-hand route retained colored failed branches and circled endpoints while continuing toward the goal; the left repeated a failed route. A “what changed?” question appeared at the result. Selecting the answer about using errors revealed an explanation. The interface describes identical maze, start, speed and first mistake; that experimental equivalence was not verified in code. See [the inspection record](updates/2026-09-30-failure-memory.md).

Use the following original design adaptation for explorable algorithms, learning toys and cause-and-effect exhibits:

1. **Separate attempt state from discovery state.** Reset the moving actor and transient animation for another attempt while preserving visited locations, known failures and their causes within the same experiment. A new world or seed must invalidate that knowledge or explicitly migrate it; stale annotations on a different maze would teach the wrong relationship. Label “retry” and “new experiment” differently.
2. **Leave a readable trace, not just a failure flash.** Mark the relevant location with a persistent shape and a short reason available on focus or selection. Distinguish current position, explored route and rejected route. Layer the moving actor above its history and allow a cleaner view when accumulated marks hide the structure. Use text or shape alongside color.
3. **Compare policies with shared inputs.** Give both processes the same generated world and initial conditions, then change the response to failure. State what counts as an attempt or inspection before showing counters. If one process finishes first, preserve its final state while the other continues or freezes with an explicit label. Do not manufacture a faster clock or easier route for the favored process.
4. **Ask before revealing the explanation.** At the meaningful divergence or outcome, keep the evidence visible and ask one question about the changed mechanism. After the response, point back to the retained trace and next action. Keep the question accessible and skippable. Present this as an explanatory interaction, not a diagnosis of the viewer's ability or proof of an educational effect.

**Checks for a new build:** revisit a known failure; retry without losing useful evidence; start a new experiment without retaining stale marks; verify both policies consume the same initial snapshot; inspect counters at matching ticks; test the explanation without relying on color or sound. The source demo's manual dead-end revisit, seed handling and counter definitions were not verified.

**Adapted prompt:** Design a [system] where failed attempts leave useful evidence. Compare two responses to the same failure under shared conditions. Keep the trace visible, ask the viewer to identify the changed process before explaining it, and distinguish retry from a new experiment. Verify those state transitions and label all scientific or learning-effect claims separately.

## Show intention, constraint and response separately

[PID Flight Lab](https://pid-flight-lab.netlify.app/), linked by its [September 28 creator post](https://x.com/lukaszsamson/status/2104680852366262458), explicitly credits Opus 5.5. Its integral-windup lesson was exercised live: the paused result showed altitude above its target, a large integral term, a capped thrust plot and a red path segment. Changing anti-windup to clamping and replaying preserved that choice while resetting the flight. Selected public inline code confirms separate requested output, bounded command and lagged physical thrust; a historical saturation flag colors path segments. This is not a scientific validation of the controller. See [the inspection record](updates/2026-09-30-intent-constraint-response.md).

Original design adaptation for responsive sculptures, machine explainers and simulation toys:

1. **Expose the constraint that causes the surprise.** Store a requested value, a constrained command and an applied value separately. A motor, spring, sound envelope or camera can have a limit and a response delay. Avoid presenting the requested value as the achieved result. Use a compact ghost mark for intention, a band for the allowed range and a solid mark for the actual response, with explicit labels and units where meaningful.
2. **Make invisible accumulation legible.** When a hidden quantity such as stored error, pressure or charge explains a later burst, give it a restrained local indicator. Pair the moment it accumulates with the constraint holding the object back. Reveal detail on focus rather than letting every measurement compete with the moving subject. The source uses synchronized plots; local glyphs are this skill's adaptation.
3. **Attach cause to historical motion.** Record the relevant condition with each trail sample. Render constrained segments differently from unconstrained segments using texture or markers as well as color. Do not recolor the whole past trajectory based on the current condition. Define trail lifetime and clear it with its owning run; keep decorative wind or wobble separate from measured motion.
4. **Replay the scenario while preserving the chosen experiment.** Separate scenario initial conditions, learner-adjusted parameters and transient state. A replay can keep the policy and gains while resetting position, accumulated state, clock and event schedule. Label a different control for restoring the lesson defaults. If claiming a controlled comparison, hold the noise sequence, disturbances and initial conditions fixed; the inspected demo uses unseeded noise, so its replays are not identical-input trials.
5. **Make the limits of the explanation visible.** A linear stability estimate, a constrained simulation and a physical device have different assumptions. Label simplified predictions separately from observed trajectories. Do not turn a green status label into a blanket claim that every operating condition is stable.

**Tune:** command limits, response time, accumulation rate, release time, trail retention and the scale of the intention/result gap. Pick values that make one causal event clear; large overshoot is a teaching scenario, not an automatic mark of design quality.

**Failure checks:** requested values can exceed the constraint without moving the bound; applied values follow the declared response model; historic trail flags remain stable after a policy change; replay keeps only documented settings; defaults restores them deliberately; paused time does not advance the scenario; equal-input comparison uses a fixed seed or disables noise. Test input reversal and rapid replay so stale accumulated state cannot create a misleading burst.

**Adapted prompt:** Build an interactive [system] whose surprising response comes from [a limit and stored state]. Show requested, allowed and applied behavior distinctly without obscuring the subject. Let the viewer change one policy and replay the event, retaining that choice while resetting the run. Use a trace to explain when the limit was active. Label model assumptions and verify the reset and comparison conditions.
