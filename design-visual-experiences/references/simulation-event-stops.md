# Let people catch a simulation's interesting moment

Use for generative art, cellular systems, process explainers and simulations where an interesting state can pass between two displayed frames. Read alongside [simulation verdicts](simulation-verdicts.md) and [interactive scenes](interactive-3d.md).

## Evidence

[Edwin Hayward's September29 post](https://x.com/edwinhayward/status/2105022417005334692) attributes an ant-pattern gallery to Opus5.5. In [the live gallery](https://www.experimentswithai.com/ants-on-a-grid.html), selecting LLRR and enabling the mirror-image stop paused at step3,928; pressing Play paused again at3,932. The drawing showed a pink reflection line and mirrored colored cells. Jumping to the LLRL preset advanced past250,000 and resumed; pausing at304,234 showed a long ribbon leaving a dense region. Reset returned the step and colored-cell counts to zero. These are interface observations, not independent proof of the creator's mathematical survey.

Selected inline code was read: the step loop maintains a mismatch count against one fixed reflection, checks for a nonempty symmetric state after each step, and can return before completing its batch. The rendering loop limits work in chunks and elapsed time. During a jump it bypasses event-stop handling, computes toward a target, then returns to playback. It does not reconstruct state by changing the displayed step number. See [snapshot, attribution and limits](updates/2026-09-30-event-stops.md). No third-party code is bundled.

## Original implementation guidance

1. **Name the event as a state predicate.** Specify exactly what counts: a first contact, a queue crossing a limit, a symmetry condition or a settled configuration. Evaluate authoritative simulation state, not a screenshot or a rounded UI value. Exclude trivial states when appropriate, such as an empty field. Label the measured condition narrowly; a fixed-axis symmetry detector does not find every possible symmetry.
2. **Detect inside the step loop.** A render callback may advance hundreds of simulation steps. Check the predicate at each relevant step, latch the first qualifying step and stop the batch there. Return the actual number of steps performed. Flush the visual state and counters for that same step before presenting the paused result. Checking only once per screen refresh can miss a short-lived event entirely.
3. **Make resume semantics deliberate.** Decide whether “next” means the next step satisfying the predicate or the next transition from false to true. The latter needs rearming after the condition clears; otherwise a persistent condition can pause again immediately. Preserve the paused state for inspection and let the user advance intentionally. Record the event type and exact step, not just a generic paused label.
4. **Accelerate state, not just its label.** A “jump near the event” control can replay the same engine in bounded chunks, use a validated checkpoint, or load a precomputed trajectory. State which method is used. Keep progress and cancellation responsive and publish the achieved step if work stops early. Rewinding requires restoring/replaying state; it is not a negative frame delta. Changing rules, seed or initial conditions invalidates old checkpoints and event locations.
5. **Separate jump and event-stop policies.** A jump may intentionally skip early events to reach a later region, while normal playback catches the next event. Make that policy apparent and define whether arrival pauses or resumes. The reference resumes after reaching a preset and ignores the mirror stop while skipping; another exhibit may need a deliberate hold instead. Do not let the same control imply both behaviors.
6. **Cache a predicate only when its update can be checked.** For a locally edited grid, maintain a count of mismatched reflected cell pairs by removing the old pair contribution and adding the new one. Choose one pair-counting convention, account for cells on the reflection axis, and rebuild the count after a reset or rule change. Compare the incremental result with a full scan on small states and random edits before trusting it. This is a general verification strategy; the reference's particular reflection and counting formula are not universal.

**Tune:** simulation steps per second, chunk size, time budget, event threshold, hysteresis/rearming, checkpoint spacing and pre-event lead-in. A UI speed target is not a measured performance guarantee. Bound computation without silently relabeling skipped simulation work as completed. For a numerical solver, detection resolution is limited by its step size unless the model supplies a more precise event time.

**Failure checks:** event occurs in the middle of a large batch; predicate stays true for several steps; event mode is enabled while already paused; jump begins with a stop enabled; cancellation or boundary exit occurs before the target; parameters change after a checkpoint; reset follows a long jump. Compare uninterrupted and chunked runs at the same step. Inspect whether view auto-scaling hides the visual change you intended people to notice.

**Adapted prompt:** Build [generative system] around [interesting state]. Add a control that catches that state inside the simulation step loop, records its exact step and holds it for inspection. Provide a separate way to approach a late event without waiting through the whole history. Define jump arrival, resume and reset behavior, and verify the event detector against a simpler reference check.
